# Anonymous Edit Tokens: one CLI-generated secret per slug, Claim as the escape hatch, mode-0600 on disk

Every Anonymous Document is bound to **exactly one Edit Token**, generated **client-side by the CLI** at first Publish — 32 bytes of `crypto/rand` as `mftk_` + base64url — and sent in the init request body as plaintext over TLS (the same trust assumption as any API key over HTTPS). The server stores only `SHA256(T)` in `documents.edit_token_hash`, discards the plaintext after persisting, and offers **no rotate endpoint, no list-tokens endpoint, and no recovery path**. Authorization on subsequent `update` / `delete` / `claim` is `Authorization: Bearer mftk_…`, verified by `subtle.ConstantTimeCompare(SHA256(presented), stored_hash)`. A lost token on an unclaimed Document is permanently unrecoverable; the URL keeps serving until the 30-day anonymous expiry (ADR-0005). The supported multi-device path is **not** token transport but **Claim**: `mdfly login` + `mdfly claim <slug>` converts the Document to Owned and NULLs `edit_token_hash` in the same transaction, after which session auth (ADR-0007) supersedes and any previously-leaked token is dead weight. `export-token` / `import-token` verbs are deferred (ADR-0014); users with a genuine need copy `~/.mdfly/credentials` manually. All CLI-held secrets — the `mfst_` session token, the per-slug `mftk_` map, the slug-keyed local state, and the opt-in `config.toml` — are **plain-text files under `~/.mdfly/` at mode 0600 with no further at-rest encryption**. The trust boundary is the **OS user account**: anything able to read your home directory (another process running as you, a `tar` backup, a cloud-sync daemon) is treated as you. `MDFLY_CONFIG_DIR` relocates the whole state directory atomically — the documented escape hatch for a home directory synced to third-party cloud storage. `mdfly logout` wipes only the session pointer by default and leaves the Edit Token map and local state intact, because Edit Tokens are bound to *anonymous Documents*, not to *your account*, and logging out should not orphan you from your own shares; `mdfly logout --wipe-local` additionally deletes `credentials` and `state.json` for the shared-PC scrub (idempotent against missing files, preserves `config.toml`), and composes as `mdfly logout --all --wipe-local` to revoke every server-side session *and* scrub the disk. The compromise response path is `mdfly logout --all` from a trusted machine, plus `mdfly claim` for any anonymous Document worth durably protecting. Token rotation without a Claim is not in v1.

We chose **CLI-generated over server-generated** tokens because a server-minted token must be returned in the init response, and a dropped ack on that response leaves the plaintext irrecoverable (the server holds only the hash) — the fix would be a server-side plaintext cache for the retry window, exactly the Redis dependency ADR-0006 eliminated. With client generation, a dropped response is recovered by plain retry: `ON CONFLICT (idempotency_key) DO NOTHING` returns the existing row and the CLI still holds the same secret. We chose **SHA256 over Argon2id/bcrypt** because the token carries 256 bits of entropy, so brute force is infeasible regardless of hash function; slow hashes exist for low-entropy human passwords and here would only buy a DoS amplifier on update/delete while giving zero real security benefit — this matches practice for high-entropy API tokens (GitHub PATs, Stripe keys). We chose **one token plus Claim** over a multi-token model with mint/revoke endpoints, because that is a real auth subsystem (tokens table, revocation list, management UI, inevitable scope creep into expiry policy and audit trails) built to serve a case Claim already handles correctly with real identity — the right answer to "I want to edit this from three machines for a year" is an account, not a fleet of anonymous secrets — and over a server-side recovery flow, because mdfly has no identity verification for Anonymous Documents, so anyone who could trigger recovery could trigger it on anyone's Document; recovery is identity-laundering by another name. We chose **mode-0600 plaintext over OS-keychain encryption** because the realistic compromise paths are malware running as you (against which keychain APIs offer essentially nothing — the malware asks the keychain too), backup or cloud-sync exfiltration (against which `MDFLY_CONFIG_DIR` outside the synced root offers real protection at zero engineering cost), and cold-disk forensics (a real keychain win, but not in this threat model), while the cost is three platform code paths, an unlock prompt that breaks the headless `--device` flow that exists precisely for headless use, and a permanent tax to keep three OS subsystems debugged; `gh`, `gcloud`, `claude`, `git`, `kubectl`, and `aws` all ship 0600 plaintext defaults under years of scrutiny. We chose **`--wipe-local` as an opt-in flag** over making it `logout`'s default because destroying the Edit Token map on every logout is a footgun in the >95% case to defend the <5% case, and we preserve `config.toml` under it because that file is opt-in, secret-free, and represents a deliberate user choice — a genuinely no-trace user can `rm -rf ~/.mdfly/`. The costs we accept: a user who loses their laptop watches an unclaimed Document become a frozen public artifact for up to 30 days; backup and sync daemons running as the user exfiltrate credentials by default, mitigated only by documented hygiene; and a leaked `mftk_` for a Document the user will not Claim is unrecoverable until expiry, since rotation is deferred. The escape hatch must stay discoverable — the publish response, `mdfly --help`, and the login help text all point at `mdfly login` + `mdfly claim` as the durable alternative.
