# Repo layout: single Go monorepo with `cmd/` + `internal/` + `apps/` reserved for future JS

v1 ships as a **single Go module monorepo** at `github.com/mdfly/mdfly` containing both binaries (`cmd/mdfly` CLI, `cmd/mdfly-server` backend) plus all shared library code under `internal/`. The tree is Go-canonical at the top level (`cmd/`, `internal/`, `go.mod`, `Dockerfile`, `.goreleaser.yaml`, `Makefile`) and reserves `apps/` for the non-Go deliverables that arrive later (`apps/landing/` for the v1.5 marketing site, `apps/dashboard/` for the v2 React SPA — each gets its own `package.json` and build pipeline alongside the Go module, with no Nx/Turborepo orchestrator until ~5+ apps justify one). Shared Go code is split across three buckets within `internal/`. **Shared** (imported by both binaries, flat under `internal/`): `slug/` (reserved-words + validation), `manifest/` (Bundle Manifest struct + content-hash logic), `markdown/` (Goldmark + chroma + bluemonday wrapper), `api/` (HTTP request/response types — the single source of truth, future codegen target for TypeScript dashboard types). **Server-only** (under `internal/server/`): runtime wiring lives at the package root — `app.go` (assembles infra clients + domain services, drives SIGINT/SIGTERM-aware graceful shutdown), `config.go` (`Config` + `LoadConfig` over env), `routes.go` (route table + middleware chain) — so `cmd/mdfly-server/main.go` is a ~30-line entrypoint over `server.LoadConfig` + `server.New` + `App.Run`. Infra + HTTP glue stay at the package root: `db/` (documents-row CRUD), `storage/` (presigned-PUT minting + HEAD-verify + blob fetch), `manifest/` (server-side bundle helpers), `httpx/` (shared HTTP error envelope), `handlers/` (thin HTTP glue per route), `middleware/` (Recover + Logger applied in routes.go). Domain logic lives under `internal/server/service/<domain>/` — one sub-package per domain (`publish/` ships today; `ssr/` for HTML templates `//go:embed`'d next to render code, `auth/` for OAuth callback + session + edit-token verification, `llm/` for `/llm/<slug>` resolver, `purge/` for Cloudflare Purge API client per ADR-0021 land as each PRD ships) so editing a domain touches its own sub-tree instead of two layer folders. **CLI-only** (under `internal/cli/`): `cmd/` (Cobra command tree), `publish/` (3-phase orchestrator), `localstate/` (state.json + credentials file I/O). SQL migrations live at root `migrations/` (golang-migrate format) because they're shared tooling — server applies in production, the dev-seed script applies locally — rather than scoped under any one binary. Infrastructure-as-code lives at root `deploy/` (Cloudflare cache rules JSON, Bulk Redirect CSV, WAF rules per ADR-0021; DO App Platform spec per ADR-0007; R2 bucket and lifecycle config) so the infrastructure diff is visible in every PR that changes the runtime contract. Build orchestration is a root `Makefile` with discoverable targets (`make build`, `make test`, `make lint`, `make migrate-up`, `make dev-seed`); no Bazel, no Nx, no script sprawl. Test fixtures live per-package in `testdata/` (Go-canonical) with root-level `testdata/` reserved for cross-package shared fixtures. The release pipeline is bifurcated by binary, not by repo: `.goreleaser.yaml` at root builds the CLI for `cmd/mdfly` into multi-arch artifacts + Homebrew tap; the root `Dockerfile` builds the server from `cmd/mdfly-server` into the image DO App Platform consumes. Both pipelines read the same `go.sum`, so dependency upgrades are atomic across the wire.

We chose **single monorepo + single `go.mod`** over polyrepo (three repos: shared module, CLI, server) because at v1 scale the wire protocol (3-phase publish from ADR-0011, idempotency-key from ADR-0013, optimistic-concurrency from ADR-0012) is shared *and* volatile — every wire change is necessarily a cross-binary edit, and forcing it through tagged semver versions of a `mdfly-shared` module creates a real version-skew hazard (CLI v1.2 + server v1.3 + shared v0.5 is a legitimate v1 failure mode in polyrepo, impossible in monorepo) and a 3-PR / 3-tag dance per wire change instead of one PR. Monorepo wins decisively while the project is solo or small-team; polyrepo earns its complexity at ~5+ contributors with conflicting release cadences, which v1's shape does not match. We chose **single `go.mod`** over Go workspaces (`go.work` with multi-module sub-trees) because workspaces solve nothing single-module doesn't here — both binaries share the same dependency graph, both want the same `go.sum`, and the workspace boilerplate would be ceremony with no payoff. We chose **`cmd/` + `internal/` Go-canonical** over uniform `apps/cli/` + `apps/server/` + `apps/landing/` + `apps/dashboard/` (the "everything is an app, symmetric polyglot" layout) because the v1 reality is Go-only and Go developers parse `cmd/<binary>/main.go` instantly; forcing JS-monorepo conventions on Go costs readability today for a symmetry payoff that 1-or-2 future JS apps don't earn. The migration to uniform `apps/` is mechanical (`git mv cmd/mdfly apps/cli/` + update `Dockerfile`/`goreleaser`) if the future demands it, so we're not painting ourselves into a corner. We chose **`apps/landing/` and `apps/dashboard/` reserved upfront** rather than reactively added later because the directory's mere existence in `CONTEXT.md` + this ADR fixes the eventual layout decision now, preventing a v2 contributor from bikeshedding over whether dashboard goes at root or under `frontend/` or somewhere worse. We chose **`internal/api/` as the wire-types source of truth** over hand-maintained TS in a future dashboard repo because the v2 plan ships a React dashboard that must consume the same API the CLI does, and Go-struct-as-canonical + `go generate` + openapi-typescript is the only path that doesn't introduce a hand-sync drift hazard — and that codegen requires both sides in the same repo to be reliable. We chose **`migrations/` at root** over `internal/db/migrations/` because migrations are shared tooling (production server applies them, dev scripts apply them locally, CI applies them on ephemeral DBs) and they should be runnable without importing the server's package graph. We chose **`deploy/` umbrella for IaC** over scattering it (Cloudflare config in `cloudflare/`, DO spec in `do/`, etc.) because every IaC change shares the same review concern: "does this PR change the production runtime contract?" Grouping them at one path makes that question one CODEOWNERS line. We chose **`internal/server/` and `internal/cli/` sub-namespaces** over flat `internal/` for all packages because binary-scoped packages (`db`, `storage`, `ssr`, `handlers` vs. `cmd`, `publish`, `localstate`) should not be importable by the other binary — their names alone are insufficient signal and a flat layout gives no visual confirmation of the consumer contract; the sub-namespace makes the intended consumer visible at a glance and prevents a future contributor from accidentally pulling a Postgres adapter into the CLI binary. Packages used by both binaries stay flat in `internal/` (`api`, `manifest`, `markdown`, `slug`) because an `internal/shared/` sub-directory would be redundant ceremony — flat-internal-equals-shared is the Go-natural assumption and the extra path segment buys nothing. We chose **flat `internal/` (not `internal/shared/`)** for the shared packages over a symmetric three-way `server/` + `cli/` + `shared/` layout because Go developers read `internal/manifest` as "private shared module" without ceremony; only the scoping-down packages (`server/`, `cli/`) need explicit naming since they restrict consumption rather than advertising it. The honest costs we accept: (a) CI runs both Go test suites on every PR even if the change is one-binary-scoped — fast enough at v1, becomes parallelizable if it ever isn't; (b) repo grows when `apps/landing/` and `apps/dashboard/` arrive and JS contributors clone Go they'll never touch — accepted as the price of atomic-wire-change agility; (c) the `cmd/<binary>` vs `apps/<binary>` asymmetry between Go and JS deliverables is real and breaks pure symmetry — accepted because Go-canonical is right for v1's reality and the future is just `apps/<jsthing>` next to it; (d) IDE indexing covers more files than a polyrepo would — modern IDEs handle this fine; (e) if v2 ever sprouts ~5+ deployables or hires per-binary owners with conflicting cadences, the polyrepo split becomes correct and the migration is real work (CI rewiring, ADR updates, broken cross-refs) — accepted as a deliberately-deferred future cost in exchange for v1+v2 simplicity now.
