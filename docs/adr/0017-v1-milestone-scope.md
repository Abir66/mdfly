# v1 milestone scope: ship the core publish/own/claim loop, defer everything social

The v1 cut of mdfly ships exactly the pieces needed to validate the core product loop — *publish a markdown file from CLI, share a URL, optionally claim it under an account* — and nothing else. **In v1:** `publish` / `update` / `delete` end-to-end via the 3-phase wire protocol (ADR-0011) with idempotency-key replay (ADR-0013) and optimistic concurrency (ADR-0012); Anonymous Documents with CLI-generated Edit Tokens (ADR-0015) and the 30-day expiry cron; Owned Documents via GitHub OAuth loopback login with `--device` fallback (ADR-0016); the `claim` flow that promotes an Anonymous Document to Owned; the flat global slug namespace (ADR-0010) with a reserved-word blocklist; the view path's backend HTML shell + SPA + R2 fetch via `cdn.mdfly.dev` (ADR-0009); GFM markdown with frontmatter, Mermaid, KaTeX, and raw-HTML stripping; server-emitted OpenGraph Preview Metadata; the CLI command surface `publish` / `update` / `delete` / `remove` / `claim` / `login` / `logout` / `whoami` / `list` plus the bare-file dispatch sugar (ADR-0014) and `MDFLY_TOKEN` env override; soft-delete with `410 Gone`; Bundle Limits enforcement for both anon and owned tiers; goreleaser-driven distribution via GitHub Releases + Homebrew tap + curl install script; DO App Platform deploy with `/healthz` (ADR-0007). Crude per-IP token-bucket rate limiting on `/api/publish/init` (~30/hr anon, ~300/hr authed). A static `mdfly.dev/abuse` page with an email mailto and a documented manual takedown process. A mobile-responsive viewer as a baseline (not a feature). **Deferred to v2:** the browser dashboard at `mdfly.dev/dashboard`; Google OAuth and any non-GitHub provider; `mdfly link --provider`; `mdfly sessions list` / `sessions revoke`; named/scoped API keys (the session token doubles as a CI credential in v1); `mdfly preview` (local render); `mdfly export-token` / `mdfly import-token` (manual cross-machine Edit Token movement — users move credentials by copying `~/.mdfly/credentials` or by Claiming the Document); cross-document Asset garbage collection (within-slug orphan cleanup on Update is in; cross-doc dedup was never chosen so cross-doc GC does not apply); view counters, analytics, custom domains, org/team docs, comments, search, edit history, dark mode and theming, publish webhooks, self-serve account deletion (manual under <1000 users), and `mdfly doctor`.

We chose this scope over (a) **anon-only beta first, identity in v1.1**: the `claim` mechanic is the most interesting product idea in the design — converting throwaway shares into owned content is the differentiating story — so stripping it from v1 hides the actual product from feedback and turns the beta into a worse Pastebin; we'd also be deferring all the OAuth machinery that's already designed (ADR-0016), and replaying that design + impl work later costs more than building it once now while every decision is fresh. We chose this over (b) **wider v1 with Google OAuth, dashboard, view counters**: each additional provider requires its own OAuth-app provisioning, callback testing, and per-provider failure-mode handling, and a single-provider-at-launch is the smallest validation of the multi-provider abstraction in ADR-0016 that still exercises it; the dashboard is a separate frontend deliverable with its own session-cookie path that doesn't share code with the SPA viewer, and shipping it pre-validation risks polishing surfaces nobody uses; view counters and analytics are write-heavy on the view path (today the view path is a static R2 fetch through Cloudflare with zero backend hops — adding a counter increment moves every page view into the backend's hot path), so we want real usage data before we commit to that infra shape. We chose to **defer `mdfly preview`** (reversing an earlier inclination to include it) because shipping the SPA's GFM + Mermaid + KaTeX + sanitizer pipeline a second time inside the Go binary (via embedded WASM or a Node sidecar) is a substantial engineering cost paid for one feature that has cheap workarounds — slug-stable + non-version-history means `publish` once then `update` repeatedly to iterate is fine, and a future enhancement can render the SPA into a static HTML snapshot for offline preview without needing render-parity in two languages. We chose to **defer `export-token` / `import-token`** because Claim is the durable multi-device path (ADR-0015 already names it the supported route), and users with a genuine need to move an Anonymous slug between machines can copy `~/.mdfly/credentials` manually — the dedicated verbs were ergonomic sugar, not enabling infrastructure, and removing them shrinks the v1 CLI surface area without removing any capability. We chose to **include crude rate limiting** over deferring it because the abuse vector is asymmetric: a scripted attacker can slug-squat the global namespace (`/notes`, `/readme`, `/blog`, …) for the cost of a few cents in R2 PUTs, and recovering squatted slugs requires either ADR-0002 reversal (slug stable forever) or manual ops intervention — both bad outcomes; a per-IP token bucket is ~50 lines and blocks the obvious script-kiddie case without committing to a tiered abuse-detection system that should be data-driven. We chose to **include an abuse / takedown page** over deferring because hosting public user content without a documented takedown path is a legal exposure regardless of user count, and a static page with a mailto + a manual process is the floor — anything cheaper than that is "we don't have a takedown process," which is the wrong answer. We chose to **defer self-serve account deletion** because under ~1000 users a `DELETE FROM users WHERE id = $1` ticket is faster than designing the cascade (does deleting a User hard-delete their Owned Documents? soft-delete? orphan them as Anonymous? — each option has UX implications we don't have data to settle), and rushing that decision pre-launch locks in the wrong default; GDPR-style "right to deletion" requests are vanishingly rare at our scale and a manual SLA is acceptable. The cost we accept: a v1 that lacks a browser UI entirely — every owned-tier user touches the product exclusively through the CLI — which is a deliberate filter (our launch audience is dev-leaning per the GitHub-only-OAuth choice) but does mean non-CLI-comfortable users can publish anonymously and view, but cannot meaningfully be Owned-tier users until the v2 dashboard ships. Trading dashboard polish for shipping the claim mechanic earlier is the right trade for a product whose entire pitch is "your terminal is the editor."
