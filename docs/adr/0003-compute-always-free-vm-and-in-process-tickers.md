# Backend compute: an always-on free-tier VM, periodic work as in-process tickers

The Go backend runs on a single **always-on ARM VM from a free tier that does not scale to zero and has no CPU-minute cap** (Oracle Cloud Always Free at the time of writing). The hard constraint driving this is free-tier-only — no spend. Because the process is never suspended, **all periodic work runs as in-process goroutines on `time.Ticker`**, started at boot with no external scheduler: the CDN purge-queue drain every ~15 minutes (ADR-0012) and the document lifecycle GC hourly (ADR-0005). Four **portability constraints** are held so the box stays swappable to any other host later: stateless processes (no on-disk state between requests), configuration by environment variables only (no config files, no platform-specific secret APIs), one portable `Dockerfile`, and a generic `/healthz` endpoint. The stateless-process constraint governs the **Go process, not the box**: the VM also runs sibling containers on a private bridge network — Redis for the write-path rate limiter (ADR-0013) with its own named volume, and Caddy terminating origin TLS (ADR-0011) as the only container that publishes a host port. Postgres is deliberately **not** among them: metadata lives in a managed instance off-box, reached only through `DATABASE_URL` (ADR-0005). Durable state therefore always sits in a datastore reached by a URL, never in the app container's filesystem, and changing hosts means re-standing those services rather than untangling the application. No host-specific feature — managed jobs, platform service discovery, proprietary secret stores — may be relied on.

We chose always-on-free over free-but-suspending options (a 60-CPU-minute/day capped app tier, or any scale-to-zero PaaS): a suspended process cannot run an in-process ticker, which would force every job behind an external trigger chain (edge cron → worker → an authenticated internal endpoint) and forbid fire-and-forget goroutines entirely, since anything spawned after a response returns is untracked by the platform and can be killed on idle-unload. Always-on erases both problems — tickers just run, and a detached goroutine survives to the next reboot. Job **correctness does not depend on always-on**: the durable `purge_queue` (ADR-0012) and the DB-tracked lifecycle GC (ADR-0005) both survive reboots regardless, so always-on buys the removal of the external-trigger tax, not the correctness. The honest costs we accept: we own OS patching, origin TLS, the deploy pipeline, monitoring, and backups, where a managed platform would have owned them, and each co-located datastore adds its own patching and volume-durability burden on top; free-tier providers reclaim *idle* instances on a multi-day utilisation window, and the tickers do **not** keep the box above that threshold — a 15-minute drain and an hourly GC pass on a small keyspace are microseconds of CPU, so the real guard is upgrading the tenancy to pay-as-you-go, which leaves the free-tier allowances free while exempting them from idle reclamation, with monitoring and a rebuild runbook as the fallback; ARM capacity in free tiers is scarce at provision time, so standing the VM up may need a retry loop; and a single box means a host outage is a full outage, accepted at this stage because the alternative costs money and the portability constraints make a move cheap if that trade ever flips.
