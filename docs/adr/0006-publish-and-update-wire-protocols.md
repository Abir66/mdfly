# Publish and Update wire protocols: separate paths, direct-to-R2 PUT, Postgres-only idempotency

Publish and Update are **two separate wires** under `api.mdfly.dev/v1/*` (ADR-0011), sharing leaf machinery but not endpoints.

**Publish** is three-phase and create-only — it always mints a fresh slug. *Init:* the CLI computes the Bundle Manifest locally (per-file logical path, SHA256, size, plus `root_path` and `project_root`), generates the Edit Token if this is an Anonymous Publish (ADR-0008), and `POST`s `/v1/publish/init` with `{idempotency_key, bundle, edit_token?, requested_slug?}`. The server `INSERT`s a `documents` row at `status='pending'` with the resolved slug and `SHA256(edit_token)` if present, using `ON CONFLICT (idempotency_key) DO NOTHING RETURNING` so a retry lands on the existing row, and responds `{slug, presigned_urls}`. `presigned_urls` maps a **representative** bundle path per R2 blobkey (`slug+hash+ext`) to a presigned PUT that pins `Content-Length` and `x-amz-checksum-sha256` into the V4 signature, expires in 10 minutes, and writes only to the server-chosen key `documents/<slug>/<hash>.<ext>` — paths sharing a blobkey with a representative are absent and covered by its upload. The CLI can neither redirect the upload nor smuggle bytes that hash to something else. *Upload:* the CLI PUTs each missing blob directly to R2, which rejects mismatched bytes itself, so junk never lands in the bucket. *Commit:* the CLI `POST`s `/v1/publish/commit` with `{idempotency_key}`; the server finds the row by that key, HEAD-verifies every blob in its stored manifest (size + etag sanity), atomically flips `pending → published`, and returns `{url, manifest_hash}`. A retry against an already-`published` row is success — terminal-state idempotency. The Edit Token is never echoed back; the CLI already holds it. Rows stuck at `pending` past a 1-hour grace are flipped to `abandoned` and their blobs deleted by the lifecycle GC (ADR-0005). The **inline-blob fast-path** (bundles ≤256 KB across ≤5 files collapsing upload+commit into one request) is **deferred in v1**: the `inline_blobs` / `inline_accept` wire fields are reserved for forward-compat, the CLI never emits them, and the server never sets them.

**Update** has its own `POST /v1/update/init` + `POST /v1/update/commit` and carries **no idempotency key**. `update/init` verifies the Edit Token (`Authorization: Bearer mftk_…`) or session against `documents.edit_token_hash` / ownership, runs a fail-fast optimistic pre-check, diffs the incoming manifest against the stored one by `(hash, ext)` — `ext` derived from the logical path to match the render-time blobkey — presigns PUTs only for absent blobs, and **writes nothing to Postgres**. Because new content means a new hash means a new key, uploaded blobs never collide with the live Document's, which keeps serving its old manifest throughout the upload window — no pending state, no downtime. `update/commit` resends the manifest, HEAD-verifies every blob, then performs **one atomic optimistic UPDATE** on the live row (`manifest`, `manifest_hash`, `bytes_total`, `file_count`, `updated_at`, refreshed `expires_at`), slug and URL unchanged. Concurrency control is a **three-way compare** against the row's current `manifest_hash`: `current == new_hash` → already applied, return success (retry-safe on a lost response, which is why commit resends the manifest); `current == parent_manifest_hash` → apply; otherwise **409 Conflict** with the server-side manifest, surfaced by the CLI as `Conflict: '<slug>' updated elsewhere since you started. Re-run to retry, or pass --force to overwrite.` `--force` sends a null parent and skips straight to apply. First-Publish races on a requested slug are caught by the UNIQUE constraint on `slug` and produce a distinct `slug taken` error, not a 409. The purge of both slug prefixes is enqueued in the **same transaction** as every commit and delete (ADR-0012).

We chose three-phase publish over a single multipart POST streaming the Bundle through the backend because that re-uploads every byte through our egress, defeats R2's zero-egress economics, and forfeits content-hash dedup entirely; we chose an explicit `commit` over an implicit one on last-PUT because without an atomic server-controlled transition a half-uploaded Bundle strands R2 objects in a state nothing can reason about. The accepted cost is three round trips minimum on even a trivial publish — the fast-path carve-out exists on paper for exactly that case and is deferred because a second write path is real complexity for latency we have not measured as a problem yet. We chose **Postgres uniqueness as the sole idempotency mechanism** over a Redis response cache: the pivot to CLI-generated Edit Tokens (ADR-0008) means no plaintext secret ever crosses server→CLI, so there is nothing to recover on a dropped ack, so the cache had no remaining job; `ON CONFLICT DO NOTHING` covers duplicate rows and terminal state covers commit retries. A key reused with a meaningfully different payload returns **422** so accidental collisions surface loudly rather than clobbering a row. We chose `DO NOTHING RETURNING` over `DO UPDATE` because the latter risks overwriting a row's manifest from a retry carrying stale data. We chose a **separate update wire** over reusing publish's pair (the original design) because create and update diverge at both the row operation (INSERT-pending versus atomic overwrite) and the auth model (none versus Edit-Token-required), and folding both into one conditional endpoint couples two lifecycles that evolve independently; the heavy upload and blob-verification machinery is still shared through leaf helpers, so nothing is duplicated but the routes and DTOs. We rejected staging the live row (flip to `pending` at init, promote at commit) because the read path serves only `published`, so any pre-commit mutation takes the Document down for the whole upload window — unacceptable for a URL-stable product — and we rejected staging columns or a shadow row because content-addressing already stages the new blobs safely in R2; the only thing needing atomicity is the manifest swap, which one guarded UPDATE delivers at zero schema cost, with the content hash doubling as the retry token that a `staged_idempotency_key` would otherwise provide. We chose optimistic detection over last-writer-wins because with no version history (ADR-0001) an LWW collision destroys the loser's bytes invisibly, and over pessimistic per-slug locking because a CLI that dies between init and commit strands the lock. `--force` ships day one because v1 has no `mdfly pull`, so a user staring at a 409 would otherwise be stuck. Remaining accepted costs: the manifest travels twice on update (init for the presign diff, commit to persist — it is small JSON); a resumed update re-presigns already-uploaded blobs, a harmless idempotent re-PUT of identical bytes to the same key; and blobs orphaned by a diverged or abandoned update leak in R2 until the deferred asset GC.
