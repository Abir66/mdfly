# Separate update wire with stateless, content-addressed commit

Update gets its own `POST /v1/update/init` + `POST /v1/update/commit` endpoints and DTOs, distinct from publish's — reversing ADR-0011's "update reuses the publish init/commit pair." `update/init` verifies the Edit Token (presented as `Authorization: Bearer mftk_...`, per ADR-0015/ADR-0016) against `documents.edit_token_hash`, runs a fail-fast optimistic pre-check (`parent_manifest_hash` vs the row's current `manifest_hash`), diffs the incoming manifest against the stored one by `(hash, ext)` — where `ext` is derived from the logical path, matching the render-time blobkey — and presigns PUT URLs only for blobs whose `(hash, ext)` is absent from the stored set; it writes nothing to Postgres. The CLI uploads the new blobs under the target slug's content-addressed keys (`documents/<slug>/<hash>.<ext>`), which never collide with the live document's existing blobs (new content → new hash → new key), so the published document keeps serving its old manifest and old blobs throughout the upload window. `update/commit` resends the manifest, HEAD-verifies every blob, then performs one atomic optimistic UPDATE on the live row (`manifest`, `manifest_hash`, `bytes_total`, `file_count`, `updated_at`, `expires_at`), slug and URL unchanged. There is no `idempotency_key`, no pending row, no staging column, and no migration: the new manifest hash is the idempotency token via a three-way commit compare — `current == new` → already-applied success (retry-safe on a lost response), `current == parent` → apply, otherwise **409**. `--force` sends a null parent and skips the check.

We rejected reusing publish's init/commit (ADR-0011's original recommendation) because create and update diverge at the row operation (INSERT-pending vs atomic-overwrite) and the auth model (anon-none vs Edit-Token-required), and folding both into one conditional endpoint couples two lifecycles that evolve independently; separate wires keep each path single-responsibility at the cost of two extra routes/DTOs — the heavy upload + `verifyBlobs` machinery is still shared via leaf helpers, so there is no logic duplication. We rejected the same-row staging the S33 issue first sketched (flip the live row to `pending` at init, promote at commit) because the read path serves only `status='published'` (`db.GetBySlug`), so any pre-commit mutation of the live row takes the document down (404) for the entire upload window — unacceptable for a URL-stable, swap-atomically product. We rejected staging columns / a shadow staging row (and the `staged_idempotency_key` + partial index + extra GC sweep they require) because content-addressing already stages the new blobs safely in R2 — the only thing needing atomicity is the manifest swap, which a single guarded UPDATE delivers with zero schema cost, and the manifest hash gives the retry-idempotency a `staged_idempotency_key` would otherwise provide. The accepted costs: the manifest travels twice (init for the presign diff, commit to persist — manifests are small JSON), and a resumed update re-presigns already-uploaded blobs (a harmless idempotent re-PUT of identical bytes to the same key; add an init-time R2 HEAD later if big-bundle resumes ever warrant it); orphaned blobs from a diverged or abandoned update leak in R2 until the deferred server-side asset-GC, an already-accepted v1 leak per CONTEXT [[Update]].
