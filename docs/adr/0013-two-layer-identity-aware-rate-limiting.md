# Rate limiting: edge IP limit (L1) plus identity-aware app limit on Redis (L2)

Write paths are limited twice. **L1** is the Cloudflare edge rule from ADR-0011 — 10 req/min per IP on the publish and update endpoints, IP-only, absorbing the crude flood before it reaches the origin. **L2** lives in the backend in front of `publish/init`, `update/init`, and `DELETE /v1/documents/:slug`, and is **identity-aware**: the key is the Edit Token on update and delete (the request already carries `Authorization: Bearer mftk_…`) and falls back to `CF-Connecting-IP` for anonymous publish — trusted only from Cloudflare's published IP ranges, since `RemoteAddr` behind the proxy is a Cloudflare edge IP, not the client. The store is **Redis over a pooled RESP/TCP connection** configured by a single `REDIS_URL` (a managed TLS endpoint today, `redis://127.0.0.1` if we ever self-host — a URL swap, no code change), with a bounded pool of 10 connections, 2 kept warm, and 2-second dial and command timeouts so a degradation stays bounded. Counting is **fixed-window** via one house method, `IncrementWithTTL(ops)`, which counts **all of a request's windows in a single atomic round trip** (a small server-side script that validates every key, then runs `INCR` + `EXPIRE` per window), where each key embeds a time-bucket step (`floor(now/window)`) so every window is a fresh, self-resetting key. Two windows per subject: **10/min** and **30/hr**. On any Redis error the limiter **fails open** and allows the request; a malformed `REDIS_URL`, by contrast, is a config error and fails the boot. Read paths — SSR HTML, the LLM twin, `cdn.mdfly.dev` — are **not** rate-limited at L2.

We chose **Redis** over an in-process limiter because the state must survive process restarts and be shared if the backend is ever scaled past one instance, and it is free at our scale; the "adds no ops" claim holds only for a managed instance, and self-hosting — including on the same VM as the backend — trades the network hop and the vendor for install, patching, persistence config, and monitoring, an operational cost we would be accepting explicitly. The transport is **RESP over a long-lived pool rather than per-command HTTPS REST**: REST made sense under an earlier scale-to-zero deploy target where no persistent connection could be held, but ADR-0003's always-on VM makes a pool the natural fit and per-command HTTP framing pure overhead. We chose **fixed-window with a time-bucketed key** over token-bucket or sliding-window because it collapses to `INCR` + `EXPIRE` with no read-modify-write: the bucketed key makes the window self-resetting, so `EXPIRE` exists only to garbage-collect dead keys — a missed `EXPIRE` leaks one stale key's worth of memory and can never permanently block a subject, because the next window is a different key. We chose to **batch every window into one round trip** rather than one call per window, both to halve store latency on the write path and because it is what makes "all windows are counted on every request" true: counting sequentially meant a failure on the per-minute window returned early and silently left the hourly allowance unspent, letting a caller hammer the minute window for free. We chose **fail-open** over fail-closed because rate limiting is abuse mitigation, not a correctness invariant — a Redis outage must degrade to "unthrottled" with L1 still standing at the edge, never to "all writes blocked". We chose an **identity key with IP fallback** because an Edit Token identifies the actual editor across IPs, while anonymous publish has no identity to key on and IP is the only available signal. We chose **not to limit reads** because an edge-cache hit costs the origin nothing and a miss is cheap and idempotent, so the abuse reads enable is already bounded by L1. The concrete threat this defends is slug-squatting: a scripted attacker could grab `/notes`, `/readme`, `/blog` and so on for the cost of a few cents in R2 PUTs, and recovering squatted slugs would require either reversing ADR-0001's slug-stability guarantee or manual ops intervention — both bad. The costs we accept: two limiters mean two places to reason about a 429; the L2 fallback trusts a header, which is only sound because the origin is reachable only through Cloudflare under ADR-0011's posture; fixed windows allow a burst straddling a bucket boundary to briefly exceed the nominal rate; and the thresholds are guesses that should be revisited against real telemetry rather than tuned in advance.
