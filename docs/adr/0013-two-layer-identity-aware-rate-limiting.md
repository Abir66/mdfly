# Rate limiting: edge IP limit (L1) plus identity-aware app limit on Redis (L2)

Write paths are limited twice. **L1** is the Cloudflare edge rule from ADR-0011 — per-IP on the publish and update paths, IP-only, absorbing the crude flood before it reaches the origin; its window is plan-bound rather than chosen (Free permits one rule, a 10-second count, and a 10-second block), so L1 is a flood absorber and never a substitute for L2's actual policy. **L2** lives in the backend in front of `publish/init`, `update/init`, and `DELETE /v1/documents/:slug`, and is **identity-aware**: the key is the Edit Token on update and delete (the request already carries `Authorization: Bearer mftk_…`) and falls back to `CF-Connecting-IP` for anonymous publish — trusted only from a **trusted proxy**, since `RemoteAddr` behind the proxy is never the client. Two peers qualify: a Cloudflare edge address, and a loopback or private address, which is the origin's own Caddy TLS terminator (ADR-0011) and cannot be routed in from the internet. Caddy holds the outer half of the chain by stripping the header when its own peer is not Cloudflare, so only the edge can name a client. The store is **Redis self-hosted on the backend's own VM** (ADR-0003) as a sibling container, reached over a pooled RESP/TCP connection configured by a single `REDIS_URL` — `redis://redis:6379` today, `rediss://` for a managed endpoint if we ever move off-box, a URL swap with no code change — with a bounded pool of 10 connections, 2 kept warm, and 2-second dial and command timeouts so a degradation stays bounded. That Redis is **durable and memory-capped**: AOF on with `appendfsync everysec` (a crash loses at most one second of counting), periodic RDB snapshots for a copyable backup artifact, `maxmemory 512mb`, and `maxmemory-policy volatile-lru` so memory pressure evicts TTL-bearing keys — which every rate-limit key is by construction — before anything without a TTL. Its port is **never published to the host**, so it is reachable only on the Docker bridge network, with `requirepass` as defence in depth. Counting is **fixed-window** via one house method, `IncrementWithTTL(ops)`, which counts **all of a request's windows in a single atomic round trip** (a small server-side script that validates every key, then runs `INCR` + `EXPIRE` per window), where each key embeds a time-bucket step (`floor(now/window)`) so every window is a fresh, self-resetting key. Two windows per subject: **10/min** and **30/hr**. On any Redis error the limiter **fails open** and allows the request — including the `OOM command not allowed` reply if the memory cap is ever reached with nothing volatile left to shed, so a full Redis degrades to unthrottled rather than to blocked writes; a malformed `REDIS_URL`, by contrast, is a config error and fails the boot. Read paths — SSR HTML, the LLM twin, `storage.mdfly.dev` — are **not** rate-limited at L2.

We chose **Redis** over an in-process limiter because the state must survive process restarts and be shared if the backend is ever scaled past one instance. We chose to **self-host it on the backend's own VM** rather than rent a managed serverless instance: a managed endpoint puts a 10–50 ms TLS round trip on every write request where a loopback socket is sub-millisecond, and it adds a vendor with a monthly command quota to a service whose hard constraint is free-tier-only. The ops we take on in exchange are narrow because the workload is tiny, and the two costs usually quoted against self-hosting nearly vanish at this size: the AOF-rewrite fork that makes operators nervous about large instances never fires on a keyspace of tens of megabytes (`auto-aof-rewrite-min-size` is 64 MB and we will not reach it), and origin TLS plus credential rotation are moot when the socket never leaves the box. What is left is package updates and a disk-full alert. What we do accept is that a VM rebuild loses the counters and a host outage takes Redis down alongside the backend — both bounded by fail-open with the L1 edge limit still standing. We chose **durability the limiter does not need**: counters are worthless after a crash, since fail-open means a restart with an empty keyspace merely grants every subject a fresh window, but persistence is two lines of config and zero code and it keeps the door open for the first piece of state that genuinely must survive. That forward-looking choice is what forces **`volatile-lru` over `allkeys-lru`**: under `allkeys-lru` a burst of limiter traffic could evict durable data to make room for throwaway counters, which is exactly backwards. Because every limiter key carries a TTL by construction and durable data would not, `volatile-lru` makes the disposable keys the entire eviction pool. Its cost is the OOM reply above — for the limiter just another fail-open error, and for a future durable user an explicit signal to handle rather than silent data loss to discover later. The transport is **RESP over a long-lived pool rather than per-command HTTPS REST**: REST made sense under an earlier scale-to-zero deploy target where no persistent connection could be held, but ADR-0003's always-on VM makes a pool the natural fit and per-command HTTP framing pure overhead. We chose **fixed-window with a time-bucketed key** over token-bucket or sliding-window because it collapses to `INCR` + `EXPIRE` with no read-modify-write: the bucketed key makes the window self-resetting, so `EXPIRE` exists only to garbage-collect dead keys — a missed `EXPIRE` leaks one stale key's worth of memory and can never permanently block a subject, because the next window is a different key. We chose to **batch every window into one round trip** rather than one call per window, both to halve store latency on the write path and because it is what makes "all windows are counted on every request" true: counting sequentially meant a failure on the per-minute window returned early and silently left the hourly allowance unspent, letting a caller hammer the minute window for free. We chose **fail-open** over fail-closed because rate limiting is abuse mitigation, not a correctness invariant — a Redis outage must degrade to "unthrottled" with L1 still standing at the edge, never to "all writes blocked". We chose an **identity key with IP fallback** because an Edit Token identifies the actual editor across IPs, while anonymous publish has no identity to key on and IP is the only available signal. We chose **not to limit reads** because an edge-cache hit costs the origin nothing and a miss is cheap and idempotent, so the abuse reads enable is already bounded by L1. The concrete threat this defends is slug-squatting: a scripted attacker could grab `/notes`, `/readme`, `/blog` and so on for the cost of a few cents in R2 PUTs, and recovering squatted slugs would require either reversing ADR-0001's slug-stability guarantee or manual ops intervention — both bad. The costs we accept: two limiters mean two places to reason about a 429; the L2 fallback trusts a header, which is only sound because two layers cooperate — Caddy strips it from a direct caller and the origin is reachable only through Cloudflare under ADR-0011's posture — and it puts the same Cloudflare IP list in two places, the Caddyfile and `clientip.go`, that must be refreshed together; fixed windows allow a burst straddling a bucket boundary to briefly exceed the nominal rate; and the thresholds are guesses that should be revisited against real telemetry rather than tuned in advance.
