# Apex routing via Cloudflare Worker + Pages, subdomain split (`api.`, `app.`, `cdn.`)

**Amends ADR-0018 and ADR-0021 in place.**

`mdfly.dev` now serves five distinct hosts with different origins, dispatched at the edge: the **apex** (`mdfly.dev`) is fronted by a **Cloudflare Worker** that routes between two origins — **Cloudflare Pages** (hosting the static landing site built from `apps/landing/` per ADR-0022) for marketing and legal pages, and the **Go backend** (DO App Platform) for Document SSR and the LLM twin; `www.mdfly.dev` continues to 301 → apex via Cloudflare Bulk Redirect (ADR-0021, unchanged); `api.mdfly.dev/v1/*` exposes the HTTP API surface directly to the backend with no Worker on the path; `cdn.mdfly.dev/*` exposes R2 via the custom-domain connector (ADR-0021, unchanged); and `app.mdfly.dev` is reserved for the v2 React dashboard (DNS unprovisioned in v1, so `app.mdfly.dev` returns NXDOMAIN until v2 lands). The apex Worker dispatches by exact-path match against a small static set — `/`, `/about`, `/pricing`, `/terms`, `/privacy`, `/contact`, `/abuse`, `/robots.txt` — plus the prefix `/_landing/*` for static assets (CSS/JS/images namespaced to keep apex path room clean), routing all of those to the Pages origin (`<project>.pages.dev`); every other path flows to the backend origin (`<app>.ondigitalocean.app`), which handles the slug catchall (`/<slug>[/<logical-path>]`), the LLM twin prefix (`/llm/<slug>[/<path>.md]`), the OAuth landing pad (`/cli/login`), and `/healthz`. The Worker's static-route table is **code-generated** from the same source that backs `internal/slug/reserved.go` so the apex path namespace and the reserved-words blocklist cannot drift; landing-page paths and the slug-reserved-words list are the same list with extra metadata (which routes Pages serves vs which routes Worker forwards to backend). The CLI's `MDFLY_API` default flips from `https://mdfly.dev` to `https://api.mdfly.dev/v1` and every endpoint in the [[API Surface]] table now reads `api.mdfly.dev/v1/*` rather than `mdfly.dev/api/v1/*`. The OAuth callback URL the backend redirects to (`http://127.0.0.1:<port>/callback?code=...`) is unchanged — it points at the CLI's loopback server, not at any mdfly host. CORS on `api.mdfly.dev` allowlists `https://app.mdfly.dev` (v2) and the local-dev origin (`http://localhost:5173` or whatever Vite picks); CLI requests carry no `Origin` header and are unaffected. Edge cache rules (ADR-0021) apply per host: `api.mdfly.dev` = blanket cache-bypass (no path-based exception needed now that API lives on its own subdomain); `mdfly.dev` keeps the slug-HTML and LLM-twin `s-maxage=86400` rules, with the Worker's static-route forwards inheriting Pages' default cache (static assets versioned by hash, HTML cached short with purge-on-deploy); `cdn.mdfly.dev` caches forever from the R2 PUT-time `immutable` header. Purge-on-commit (ADR-0021) now targets only the slug-HTML and LLM-twin patterns; the Worker dispatch table is read-only at runtime and does not need invalidation per commit.

We chose **Worker + Pages at apex** over **embed-landing-in-backend** because while edge cache absorbs landing-route load on backend (the load concern was the user's stated motivation but isn't actually a load problem — `s-maxage=86400` means ~3000 backend hits/day for 10 landing routes across 300 Cloudflare data centers, trivial), the *operational* benefits of separation are real: marketing copy and backend code change at different cadences (weekly vs monthly), have different security postures (static HTML can't leak secrets, the Go backend has API keys + DB credentials), can be PR'd by different people (a copywriter PRs `apps/landing/` without ever opening a Go file), and Pages' free tier handles unlimited bandwidth for static assets while backend bandwidth runs through DO's paid plan. The Worker is the smallest possible glue (~20 lines, well under the 100k req/day free tier — and at our v1 scale we will not approach that limit). We chose **`api.mdfly.dev` over `mdfly.dev/api/v1/*`** for three concrete reasons: (a) the v2 dashboard at `app.mdfly.dev` calling a same-origin API at `mdfly.dev/api/v1/*` mixes HTML and API cache rules awkwardly on one host (cache-everything for some paths, never-cache for others — fragile), whereas `api.mdfly.dev` is a blanket cache-bypass with no exceptions; (b) CORS for `app.mdfly.dev → api.mdfly.dev` is a single explicit Origin allowlist that browsers handle naturally, whereas same-origin API endpoints would still require Origin checks because the API is a different security domain (Authorization-bearing) than the HTML; (c) user-facing-vs-machine-facing separation is honest — putting `api` in the URL bar tells operators "this is the machine interface" without ambiguity. We chose to **provision `app.mdfly.dev` only at v2** rather than serving a "coming soon" placeholder because a placeholder is engineering tax (build, deploy, monitor for a page nobody visits) and NXDOMAIN is the correct truthful state — no DNS, no host, no expectation. We chose **`_landing/` prefix for landing static assets** rather than serving them from `cdn.mdfly.dev/landing/*` because keeping landing's CSS/JS/images on the same origin as the landing HTML simplifies the Pages deploy pipeline (no second R2 upload step, no separate cache strategy) and the `_` prefix is already in the [[Reserved Words]] blocklist (so the slug namespace is collision-proof). We chose **code-generation of the Worker's static-route table from `internal/slug/reserved.go`** over hand-maintained parallel lists because drift between the two (a path added to landing but not reserved as a slug, or a slug minted by a stale blocklist) is a class of bug that should be made impossible by construction rather than caught in review. We chose **www→apex via Bulk Redirect, not via Worker** because the redirect logic is too trivial to spend a Worker invocation on (Bulk Redirect runs entirely at edge, no Worker billing/quota). The honest costs we accept: (a) the apex is no longer single-origin — a problem manifesting as "slug page renders but landing 500s" requires checking three origins (Worker, Pages, backend) instead of one; offset by clear DNS/host-based blame and Cloudflare's Real-User Monitoring built in; (b) Worker on the hot path for every apex request adds ~1-3ms latency, well under the human-perceptible threshold; (c) Worker logic lives in JavaScript while the rest of the codebase is Go — accepted as a tiny well-bounded interface; (d) Pages free tier has limits we'll hit only at massive marketing scale (500 build minutes/month, 20k files per deploy) — irrelevant at v1; (e) the API URL changing from `mdfly.dev/api/v1/*` to `api.mdfly.dev/v1/*` is a breaking change for any CLI version that's already been distributed — accepted because we haven't shipped any CLI yet, so there's nothing to break; (f) ADR-0018's apex routing description and ADR-0021's apex cache rules each become technically stale until amended — handled by the amendment note on this ADR and inline edits.
