# Backend compute: Oracle Cloud Always Free VM + in-process ticker scheduler

**Status: accepted — supersedes ADR-0007** (DO App Platform, which assumed DO student credit; the hard constraint is now free-tier-only, no spend).

The Go backend runs on an **Oracle Cloud Always Free** ARM VM — always-on, no scale-to-zero, no CPU-minute cap. All periodic work runs as **in-process goroutines on `time.Ticker`**, started at boot, with no external scheduler: the CDN purge-queue drain (~15 min, ADR-0031) and the document lifecycle GC (hourly, ADR-0030). The four ADR-0007 portability constraints — stateless processes, env-var-only config, a single portable Dockerfile, and a generic `/healthz` endpoint — are **retained**, so the box stays swappable to any other host later.

We chose **Oracle Always Free** (genuinely free *and* always-on) over **Azure App Service F1** (free but a **60 CPU-minute/day hard cap** plus scale-to-zero idle-unload) and over Render / Cloud Run (also scale-to-zero). Scale-to-zero was the disqualifier: a suspended process cannot run an in-process ticker, which would force every job behind an external trigger (Cloudflare Cron → Worker → an authenticated internal endpoint) and forbid fire-and-forget goroutines entirely — anything spawned after a response returns is untracked by the platform and can be killed on idle-unload. Always-on erases all of that: tickers just run, and a detached goroutine survives until the next reboot. The honest costs we accept: we own OS patching, TLS, the deploy pipeline, monitoring, and backups (versus DO/PaaS-managed); Oracle reclaims *idle* Always Free VMs, so the tickers plus real traffic must keep the box above the idle threshold; and ARM A1 capacity is scarce at provision time, so standing the VM up may need a retry loop. Job **correctness does not depend on always-on** — the durable `purge_queue` (ADR-0031) and the DB-tracked GC (ADR-0030) both survive reboots regardless; always-on only removes the external-trigger tax and the "will my goroutine be killed" hazard.
