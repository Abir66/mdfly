# Idempotency-Key column on documents with Postgres UNIQUE constraint

The CLI generates a fresh UUIDv4 per `mdfly publish` invocation and sends it as the `Idempotency-Key` HTTP header on both `/api/publish/init` and `/api/publish/commit`. The `documents` table carries an `idempotency_key UUID UNIQUE` column; the init endpoint runs `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING *`. A retry of a successful-but-network-dropped init lands on the existing row and returns the same `slug` (and same missing-hash / presigned-URL list, recomputed cheaply from the row's manifest) without creating a duplicate Document. The CLI's automatic retry policy on init and commit (3 attempts, exponential backoff on 5xx/timeout) reuses the same `Idempotency-Key` across attempts. The commit endpoint identifies the target row by `WHERE idempotency_key = $1 AND status = 'pending'` and flips it to `published`; a retry where the row is already `published` is treated as success and returns the same URL — natural idempotency from the row's terminal state. A key reused with a meaningfully different payload (different manifest hash, different requested slug) returns **422** so accidental collisions surface loudly. There is no `Idempotency-Key` response cache and no Redis dependency on the write path — Postgres uniqueness is the sole idempotency mechanism.

This ADR replaces the earlier Redis-backed response-cache design. The pivot was driven by ADR-0015's switch to CLI-generated Edit Tokens: once the secret is minted client-side, no plaintext ever crosses the server→CLI response, so there is no plaintext to recover on a dropped ack, so there is no reason to cache responses in Redis. Postgres `ON CONFLICT` covers the remaining concern (same `Idempotency-Key` must not produce a second row), and Postgres `WHERE status = 'pending'` covers the commit-retry case (already-published rows treat retries as no-op success). We chose this over (a) keeping the Redis response cache despite the pivot: dead weight, adds infra criticality for no remaining benefit. We chose this over (b) `ON CONFLICT DO UPDATE` semantics: less clear than `DO NOTHING RETURNING` paired with a fresh SELECT, and risks accidentally clobbering a row's manifest on a retry that arrived with stale data. The cost: an extra UUID column with a UNIQUE index on `documents`, and a small cron job that deletes rows stuck in `status='pending'` for >1 hour (CLI died mid-publish, never sent commit). Redis remains in the stack only for the view-shell manifest cache from ADR-0001, where it is a perf cache holding no secrets.
