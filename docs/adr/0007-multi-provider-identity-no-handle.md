# Identity: multi-provider OAuth over loopback, no mdfly-owned handle

Identity is provider-agnostic and OAuth-based — **GitHub at v1 launch, Google to follow**, further providers addable without a schema change. The data model splits identity from user: `users` is the canonical mdfly account, `identities (user_id, provider, provider_id, email)` keyed on `(provider, provider_id)` is a join table where each authenticated provider login is one row pointing at one `users` row (ADR-0005). There is **no mdfly-minted handle**: URLs are `mdfly.dev/<slug>` (ADR-0001), attribution renders the provider's `display_name`, and v1 has no profile pages, so no globally-unique user-chosen identifier is needed. `display_name` is denormalized from the **first** linked identity and stays stable thereafter, so multi-provider users do not see their name flicker; `primary_email` is nullable (some providers return only a `noreply` alias) and is never a unique key. Account linking is **explicit only** — `mdfly link --provider <name>` from an authenticated session attaches a second `identities` row to the current user; matching by email across providers is never automatic, and a link attempt hitting a row already attached to a different user is rejected with 409. The primary login flow is **loopback OAuth code flow** (RFC 8252): `mdfly login` binds a localhost server on an OS-assigned ephemeral port, opens the browser to `mdfly.dev/cli/login?port=<p>&state=<csrf>`, the user picks a provider on the mdfly-hosted chooser page, completes OAuth in-browser, the backend redirects to `http://127.0.0.1:<p>/callback?code=<mfxc_…>&state=<csrf>` carrying a **single-use 60-second exchange code**, the CLI's local server captures it and `POST`s `/v1/auth/cli/exchange` to receive the real session token `mfst_<32B base64url>`, and the browser shows a "you can close this" page. The session row is the same shape whether the client is CLI or browser (`client_kind ∈ {cli, browser}`, `token_hash = SHA256(mfst_…)`, optional `device_label` from `--label`), with the session **pre-created at OAuth callback time** and its id written into `exchange_codes`. For headless environments (SSH, Docker, CI) `mdfly login --device` falls back to OAuth device flow against the same provider endpoints, terminating in the same `sessions` insert. In v1 the session token doubles as the CI credential (read from `MDFLY_TOKEN` first, then the credentials file); named scoped API keys are deferred. The v2 dashboard at `app.mdfly.dev` reuses this same backend code flow with cookie-based delivery (`HttpOnly`, `Secure`, `SameSite=Lax`), but state-changing API calls **always** require the token in the `Authorization` header even when a cookie is present, which removes CSRF surface from write endpoints.

We chose multi-provider now over **staying GitHub-only** (the original position) because closing the door on non-GitHub users is a permanent product-shape choice we do not want this early, and because adding a second provider later means either ugly nullable columns or a painful migration to the join-table layout — paying that migration now, at zero rows, is free. We chose **no handle** over a mdfly-owned handle namespace because handles only earn their cost when they appear in URLs or `@mentions`, neither of which exist, while minting one immediately invites collisions with the slug namespace, uniqueness arbitration UX, rename policy, and squatting fights, all to drive zero v1 features. We chose **explicit linking** over auto-link-by-email because same-email auto-linking is a known account-takeover footgun (an attacker who controls one provider's verified email claims the other's account on first login); "your two accounts are separate until you link them" is recoverable, "we silently merged your accounts" is not. We chose **loopback as the primary CLI flow** over device flow because retyping a `user_code` is worse UX than clicking a provider button, and `claude` / `gh` / `gcloud` have normalized loopback as the expected CLI pattern; device flow is retained behind `--device` because it is the only flow that works headless. We chose a **hosted provider chooser** at `/cli/login` over forcing `--provider <name>` so a default invocation just works and the user can pick visually, keeping the explicit flag for scripts. We chose **exchange-code indirection** over putting the session token in the redirect URL because a token in a URL leaks into browser history, system logs, and the URL bar; the 60-second single-use `mfxc_` makes a log-leaked code worthless. We chose **DIY identity** over Clerk/Auth0/WorkOS because hosted providers optimize for browser SPA flows, hosted sign-in UIs, password resets, and MFA — none of which we use — while their CLI device-flow support is shaky and their default session lifetimes are a hard mismatch for a long-lived CLI bearer token in a credentials file; identity lock-in is forever-painful to unwind and the DIY footprint is one OAuth proxy per provider plus three tables. The costs we accept: identity is a real subsystem with per-provider OAuth-app config in deploy env, explicit link/unlink commands, a headless fallback flag, and a transient `exchange_codes` table to GC; provider lock-in is softened but not gone (a user who loses their only provider account loses access to their Owned Documents); an orphan pre-created session from a login the CLI never completed is harmless but does accumulate until a future sweep; and the v1 footprint is larger than a GitHub-only minimum, paid for auth UX users already know and a v2 dashboard that needs no auth rewrite.
