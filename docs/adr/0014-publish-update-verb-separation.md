# Separate `publish` and `update` verbs in the CLI

mdfly's CLI splits the create-vs-modify intent into two distinct verbs. `mdfly publish <file>` always mints a fresh slug and creates a brand-new Document — repeated invocations on the same file produce independent URLs, accumulating one entry per call into the file's local-state slug list (`~/.mdfly/state.json` maps `path → [slug, slug, ...]`). `mdfly update <file>` modifies an existing Document in place; it disambiguates by consulting the local slug list — zero entries errors out with a hint to publish first, one entry targets that slug, two-or-more pops an interactive picker on a TTY (or errors with a `--slug` hint in non-TTY contexts like CI). The `--slug <s>` flag is supported on `update` for explicit non-interactive targeting and to recover after a local-state loss (file moved, `~/.mdfly` wiped, new machine). The `--force` flag remains on `update` only — it bypasses the optimistic `parent_manifest_hash` check (ADR-0012). There is no `--new` flag because `publish` itself is the new-URL verb.

A bare-command shortcut `mdfly <file>` (no verb) is also supported: 0 mapped slugs dispatches to `publish`, 1 mapped slug dispatches to `update`, 2+ mapped slugs requires explicit disambiguation (interactive picker on a TTY, error on non-TTY). The shortcut prints a loud one-line summary (`Published as ...` / `Updating ...`) every run so the user always knows which path executed. The shortcut is sugar for the common case; the explicit verbs remain the canonical scriptable forms and the contract this ADR establishes.

We chose this over (a) a single `publish` verb that auto-detects "have I seen this file before?" and switches between create and update on its own: that pattern silently overwrites Documents whenever a user's mental model diverges from the CLI's heuristic (e.g. the user thought they were sharing a fresh copy but the CLI updated an old one because `~/.mdfly/state.json` still had the mapping). A wrong guess on a destructive operation costs the user real bytes, and the optimistic-concurrency check from ADR-0012 doesn't catch this — `parent_manifest_hash` will be correct because the CLI did just fetch it. The explicit-verb model makes the intent legible from the command itself: anyone reading `mdfly publish report.md` in a shell history or CI log knows a new URL was minted; `mdfly update report.md` makes the in-place modification obvious. We chose this over (b) a single `publish` verb with required `--new` / `--update` flags: that's the same information density as two verbs but uglier at the call site, and it makes the safe default ambiguous. The cost we accept: users iterating on a draft must learn two verbs instead of one — but they were going to need both anyway (publish-once-then-iterate is the iterate pattern), and "type `update` to update" is a one-time learning cost in exchange for never silently overwriting a Document.
