# Single CLI-generated Edit Token per Anonymous Document, with Claim as the multi-device escape hatch

Every Anonymous Document is bound to exactly one Edit Token. The token is generated **client-side by the CLI** at first Publish — 32 bytes of `crypto/rand` formatted as `mftk_` + base64url — and sent to the server in the `/api/publish/init` request body as plaintext over TLS (same trust assumption as any password/API key over HTTPS). The server stores only `SHA256(T)` in `documents.edit_token_hash` and discards the plaintext from RAM after persisting; there is no "rotate token" endpoint, no "list active tokens" endpoint, no server-side recovery path. The token lives client-side in `~/.mdfly/credentials` (mode 600), keyed by slug. To use the same Anonymous Document from a second machine, the user manually transports the token: `mdfly export-token <slug>` prints it, `mdfly import-token <slug> <token>` accepts it on the other end. Users who want real multi-device editing are pushed toward `mdfly login` + `mdfly claim <slug>` — claiming converts the Document to Owned status and replaces Edit-Token auth with GitHub session auth (ADR-0003), at which point multi-device is solved structurally. Authorization wire format on subsequent `update` / `delete` / `claim`: `Authorization: Bearer <token>`; server fetches the stored hash and runs `subtle.ConstantTimeCompare(SHA256(presented_token), stored_hash)`. A lost Edit Token on an unclaimed Anonymous Document is permanently unrecoverable; the URL keeps serving the content until the 30-day Anonymous-tier expiration kicks in.

CLI-generated rather than server-generated: a server-generated token would be returned in the init response, and a dropped-ack on that response leaves the token plaintext irrecoverable (server has only the hash). The fix would be a server-side cache of plaintext tokens for the retry window — exactly the Redis dependency this design eliminates (see the ADR-0013 pivot). With CLI-generated tokens, the CLI always holds the plaintext locally, so a dropped init response is recovered by simple retry: `Postgres ON CONFLICT (idempotency_key) DO NOTHING` returns the existing row's slug, and the CLI still has the same T it generated before the retry. SHA256 rather than Argon2id/bcrypt: T has 256 bits of entropy, so brute-force is infeasible regardless of hash function; slow-hashes are designed for low-entropy user-chosen passwords and would only buy a DoS amplifier on update/delete (~100ms CPU per rejected request) while giving zero real security benefit. SHA256 matches industry practice for high-entropy API tokens (GitHub PATs, Stripe keys, AWS access keys).

We chose this over (a) a multi-token model where the server tracks a per-Document list of valid tokens and supports mint/revoke endpoints: that's a real auth subsystem (tokens table, revocation list, UI to manage them, scope-creep toward expiration policies and audit trails) built to serve a use case that Claim already handles correctly with GitHub identity — the right answer for "I want to edit this from three machines for a year" is an account, not a fleet of anonymous tokens. We chose this over (b) single-token plus a server-side recovery flow (email-the-token-back-on-demand): mdfly has no identity verification for Anonymous Documents — anyone who could trigger recovery could trigger it on anyone's Document — so recovery is identity-laundering by another name. The cost we accept: a real failure mode where a user loses their laptop and their Anonymous Document becomes a frozen public artifact for up to 30 days. We judge this acceptable because (i) Anonymous is positioned as ephemeral by design (30-day expiry, ADR-0008), and (ii) the Claim path is one command away for anyone who wants durability. The escape hatch must be discoverable: the publish response and `mdfly --help` both prominently point at `mdfly login` + `mdfly claim` as the durable alternative.
