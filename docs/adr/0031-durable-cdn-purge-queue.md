# Durable CDN purge queue with retry

**Status: accepted — supersedes the purge mechanism of ADR-0021** (the fire-and-forget background goroutine). Only the purge mechanism changes; ADR-0021's TLS, DNS, cache-rule, WAF, and email-DNS decisions are unchanged.

Cache invalidation on commit (publish / update) and delete is backed by a durable **`purge_queue(slug PRIMARY KEY, enqueued_at, attempts, next_attempt_at)`** table (deduplicated by slug). The slug is **enqueued in the same transaction as the row flip**, so a committed write can never be left un-enqueued. Immediately after commit a best-effort goroutine attempts the purge inline (safe to lose — the process is always-on per ADR-0029, but nothing depends on it); an **in-process ticker (~15 min)** drains the queue with backoff via `next_attempt_at`, deleting a row on success. Purge is **by prefix** — two prefixes per slug, `mdfly.dev/<slug>` and `mdfly.dev/llm/<slug>`, each covering the bare page plus every sub-path in one operation — under the Cloudflare **Free-plan** purge limits: **5 requests/minute** (token bucket, **burst 25**), **100 operations/request** (≈ 50 slugs per call). Purge is idempotent and always re-reads the latest DB state, so a late or duplicated drain is harmless. Purge success remains **not a commit precondition** — worst case is a stale viewer up to the 24h `s-maxage`.

We chose a **durable DB queue** over ADR-0021's in-goroutine retry because the owner's constraint is that a failed purge on update/delete is *not acceptable*: a goroutine's retry state dies with the process on reboot, crash, or deploy, silently stranding stale content until the 24h TTL, whereas a DB row survives and the drain ticker retries across restarts. We chose to **enqueue transactionally and treat the inline attempt as pure fast-path** — rather than "inline first, enqueue only on failure" — so there is no window where a write commits but its purge intent is lost, and the immediate goroutine is a latency optimization that can safely be killed. We chose **prefix purge** over listing individual URLs because one prefix covers a slug's bare page and all sub-paths in a single operation (ADR-0021's four URL patterns collapse to two prefixes), staying far inside the free-plan 100-ops/request ceiling and turning the 5-req/min limit into ~250 slugs/min of headroom. We chose **Postgres, not Upstash, for the queue** — even though Upstash is already in play for rate limiting (ADR-0028) — because the queue needs durability and a transactional enqueue in the same commit transaction as the row flip; Postgres gives both, while Upstash is best-effort and eviction-prone and gives neither. The residual race we accept: a read landing in the millisecond window between the purge and the DB flip can repopulate stale cache; it is backstopped by `s-maxage` and can optionally be closed by a delayed second drain.
