# Content-hash flat storage with manifest indirection

**Amended by ADR-0018:** the original phrasing below described the SPA as the Manifest consumer. That role moved to the backend at read time. Storage layout (content-hash flat under `r2://documents/<slug>/<hash>.<ext>`), markdown-byte-identical upload, and manifest-indirection-not-link-rewrite are unchanged — only the *consumer* of the Manifest moves. The final sentence of paragraph 1 should now be read as: "At view time, the Go backend reads the Manifest from Postgres, fetches the requested markdown blob from R2, and resolves every relative reference inside markdown (`![](./logo.png)`, `[next](./b.md)`) by manifest lookup → `cdn.mdfly.dev/documents/<slug>/<hash>.<ext>` (assets) or absolute `mdfly.dev/<slug>/<path>` URLs (cross-md links)."

A published Bundle is stored as a flat content-addressed keyspace under its slug. Every file — markdown and assets alike — is hashed (SHA256) over its **raw bytes** and stored at `r2://documents/<slug>/<sha256>.<ext>`. The original directory structure and filenames are not encoded in R2 keys at all; instead they live in a **Bundle Manifest** kept in Postgres (`documents.bundle_manifest`), which maps each logical bundle-relative path (`index.md`, `b.md`, `imgs/logo.png`) to its content hash and size. The Root markdown is identified by a manifest entry pointing at the bundle-relative root path. Markdown files themselves are stored byte-identical to what the user wrote — no link rewriting occurs at upload time. At view time, the viewer SPA receives the Manifest inlined in the backend-rendered shell HTML and resolves every relative reference inside markdown (`![](./logo.png)`, `[next](./b.md)`) by manifest lookup → `cdn.mdfly.dev/documents/<slug>/<hash>.<ext>`.

We chose this over (a) link-rewrite-at-CLI (rewrite markdown to embed `<hash>.<ext>` URLs directly): under that model, changing one asset forces the markdown referencing it to be re-hashed and re-uploaded, and cycles between markdown files become a chicken-and-egg hash problem. Under manifest indirection, each file's hash is independent of every other file's hash — content integrity is end-to-end (local file bytes == stored bytes == hash), and an asset change touches exactly one R2 blob plus a Postgres manifest row. We chose this over (b) preserving original tree structure in R2 paths: content-hash filenames give us automatic CDN cache-immutability (`max-age=1y`, no invalidation logic ever) and a flat object-store keyspace with no path-traversal or case-sensitivity edge cases. The costs are real: the SPA carries a ~50-line link-resolution layer that intercepts markdown link/image rendering and routes them through the Manifest, and the backend's shell render is no longer pure-static (it must read the Manifest from Postgres per viewer hit — mitigated by Redis caching keyed on `(slug, manifest_hash)`).
