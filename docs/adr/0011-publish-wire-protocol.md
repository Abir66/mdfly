# Three-phase publish wire protocol with direct-to-R2 presigned PUT

Publish is a three-phase exchange between CLI and backend, correlated end-to-end by a single client-minted `Idempotency-Key` (UUIDv4 per `mdfly publish` invocation; see ADR-0013). **Phase 1 — Init:** CLI computes the Bundle Manifest locally (per-file logical path, SHA256, byte size, plus the root entry), generates the Edit Token if this is a new Anonymous Publish (see ADR-0015), and `POST`s to `/api/publish/init` with `{idempotency_key, bundle, edit_token?, requested_slug?, parent_manifest_hash?}` — where `bundle` is `{root_hash, files:[{path, hash, size}]}`. Server `INSERT`s a `documents` row with `status='pending'`, the resolved slug (random for Anonymous, user-chosen-or-random for Owned), and `SHA256(edit_token)` if present; the insert uses `ON CONFLICT (idempotency_key) DO NOTHING` so retries land on the existing row. Server responds with `{slug, presigned_urls}` — `presigned_urls` maps each content hash in the manifest to a presigned PUT URL that pins `Content-Length` (exact bytes from manifest) into the V4 signature, expires in 10 minutes, and writes to the server-chosen key `documents/<slug>/<hash>.<ext>`. The CLI cannot redirect the upload elsewhere or smuggle bytes that hash to something other than the declared content hash. **Phase 2 — Upload:** CLI PUTs each missing blob directly to R2; R2 itself rejects bytes that don't match the signed checksum, so junk never lands in the bucket. **Phase 3 — Commit:** CLI `POST`s `/api/publish/commit` with `{idempotency_key}`. The server identifies the row by `WHERE idempotency_key = $1`, HEAD-checks every blob in its stored manifest (size + etag sanity), and atomically flips `status='pending' → 'published'` (or replaces `bundle_manifest` on an Update with the optimistic check from ADR-0012). A retry hitting a row already in `status='published'` is treated as success and returns the same URL — natural terminal-state idempotency. The commit response is `{url, manifest_hash}` — the Edit Token is never echoed because the CLI already holds it. A cron sweep deletes rows stuck in `status='pending'` for more than 1 hour (CLI died mid-publish). An **inline fast-path** short-circuits the round trips for trivial Bundles: when the manifest total is ≤ 256 KB across ≤ 5 files, the init response sets `inline_ok: true` and the CLI inlines blob bytes into the `commit` body instead of PUTting to R2, collapsing Phase 2 + 3 into one request (server uploads the bytes to R2 server-side before flipping status).

We chose three-phase over (a) a single multipart POST that streams the whole Bundle through the backend: that pattern re-uploads every byte through our backend egress, defeats R2's zero-egress economics, and forfeits content-hash dedup entirely (every Update re-uploads every asset, even unchanged ones). We chose explicit `commit` over (b) an implicit commit on last-PUT or webhook-driven finalization: without an atomic server-controlled transition, half-uploaded Bundles strand R2 objects whose status the SPA can't reason about, and a crashed CLI leaves the slug in an indeterminate state. We accept the cost: three RTTs minimum (init + parallelizable PUTs + commit) is real latency on `mdfly publish hello.md` for trivially small Documents, hence the 256-KB / 5-file inline fast-path carve-out — which adds a second code path but covers the most-common micro-Bundle case in one network round trip. The presigned-PUT lockdown (signed `Content-Length` + signed `x-amz-checksum-sha256` + 10-minute expiry + server-chosen object key) plus an `init` rate-limit per IP+session contains the abuse surface so direct-to-R2 doesn't open a cost-burn or storage-poisoning vector. The earlier draft of this ADR returned a server-minted `upload_id` from init to carry expected hash state into commit; that became vestigial once init writes a pending row to Postgres — commit identifies the row by `idempotency_key` and reads the manifest directly from Postgres, so `upload_id` was dropped.
