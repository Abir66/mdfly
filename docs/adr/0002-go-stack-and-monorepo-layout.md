# Go for both binaries, single-module monorepo with `cmd/` + `internal/` + `apps/`

Both deliverables are Go: the `mdfly` CLI and the `mdfly-server` backend, shipped from a **single Go module monorepo** at `github.com/mdfly/mdfly`. Go for the CLI buys a single static cross-compiled binary with no runtime dependency on the user's machine; Go for the backend lets the markdown renderer, reference resolver, manifest logic, and slug validation be shared between CLI pre-flight and server re-validation instead of reimplemented. There is **no React in v1** — the viewer is server-rendered Go HTML (ADR-0010); React is reserved for the v2 dashboard. The tree is Go-canonical at the top (`cmd/`, `internal/`, `go.mod`, `Dockerfile`, `.goreleaser.yaml`, `Makefile`), with `apps/` reserved for the non-Go deliverables that arrive later (`apps/landing/` for the v1.5 marketing site, `apps/dashboard/` for the v2 SPA — each with its own `package.json`, no Nx/Turborepo until ~5+ apps justify one). `internal/` splits three ways: **shared** stays flat (`slug/` reserved-words + validation, `manifest/` Bundle Manifest + content hashing, `markdown/` Goldmark + chroma + bluemonday, `api/` wire types as the single source of truth and future TypeScript codegen target); **server-only** lives under `internal/server/` with runtime wiring at the package root (`app.go` assembles infra clients and domain services and drives signal-aware graceful shutdown, `config.go` holds `Config` + `LoadConfig` over env, `routes.go` holds the route table and middleware chain, so `cmd/mdfly-server/main.go` is a ~30-line entrypoint), infra and HTTP glue alongside it (`db/`, `storage/`, `httpx/`, `handlers/`, `middleware/`), and domain logic under `internal/server/service/<domain>/` (`publish/`, `update/`, `view/`, `auth/`, `llm/`, `purge/`); **CLI-only** lives under `internal/cli/` (`cmd/` Cobra tree, `publish/` phase orchestrator, `localstate/` state + credentials I/O). Root `migrations/` holds golang-migrate SQL (shared tooling: the server applies in production, dev scripts apply locally), root `deploy/` holds all IaC (edge cache rules, Bulk Redirect CSV, WAF rules, R2 bucket + CORS config, host provisioning) so an infrastructure diff is visible in every PR that changes the runtime contract, and a root `Makefile` carries discoverable targets (`build`, `test`, `lint`, `migrate-up`, `dev-seed`). `.goreleaser.yaml` builds the CLI into multi-arch artifacts plus a Homebrew tap; the root `Dockerfile` builds the server image. Test fixtures live per-package in `testdata/`.

We chose a single monorepo with a single `go.mod` over a polyrepo split because at this scale the wire protocol (ADR-0006) is both shared *and* volatile — every wire change is necessarily a cross-binary edit, and forcing it through tagged versions of a `mdfly-shared` module creates a genuine version-skew hazard (CLI v1.2 + server v1.3 + shared v0.5 is possible in polyrepo, impossible in monorepo) plus a three-PR dance per change. We chose a single module over Go workspaces because both binaries share one dependency graph and one `go.sum`, so `go.work` would be ceremony with no payoff. We chose Go-canonical `cmd/` + `internal/` over a symmetric polyglot `apps/cli/` + `apps/server/` layout because the v1 reality is Go-only and Go developers parse `cmd/<binary>/main.go` instantly; the migration to uniform `apps/` is mechanical (`git mv` plus Dockerfile/goreleaser edits) if a future polyglot balance ever demands it. We reserved `apps/landing/` and `apps/dashboard/` upfront rather than adding them reactively so the eventual layout is settled now and a v2 contributor cannot bikeshed it. We sub-namespaced `internal/server/` and `internal/cli/` rather than flattening everything because binary-scoped packages should not be importable by the other binary and the path segment makes the intended consumer visible at a glance, while genuinely shared packages stay flat (`internal/shared/` would be redundant — flat-internal-equals-shared is the Go-natural reading). The costs we accept: CI runs both suites on every PR even for one-binary changes (fast enough now, parallelizable later); JS contributors will clone Go they never touch once `apps/` fills; the `cmd/<binary>` versus `apps/<jsthing>` asymmetry breaks pure symmetry; and if this ever sprouts ~5+ deployables with conflicting release cadences the polyrepo split becomes correct and the migration is real work.
