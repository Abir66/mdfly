# Shared-PC threat model: OS-user account is the trust boundary, mode-0600 plaintext is the floor

The mdfly CLI persists every secret it holds — the `mfst_` session token, the per-slug `mftk_` Edit Token map, the [[Local State]] slug list, and the optional `config.toml` — as plain-text files under `~/.mdfly/` with mode `0600` and **no further at-rest encryption**. The trust boundary is the OS user account: anything able to read your home directory (another process running as you, a `tar` backup, a `Dropbox` daemon, a `find / -name credentials -print` from a curious admin) is treated as if it were you. `mdfly logout` wipes only the session pointer by default and leaves the Edit Token map plus Local State intact (Edit Tokens are bound to *anon Documents*, not to *your account* — logging out of your account should not orphan you from your own anon shares); a new `mdfly logout --wipe-local` flag additionally deletes `credentials` and `state.json` for the shared-PC scrub case (preserves `config.toml` because it is opt-in user-curated and contains no secrets), is idempotent against missing files (the point is to scrub whatever the previous user left), and composes with `--all` for the "I'm done with this machine" exit (`mdfly logout --all --wipe-local` revokes every server-side session AND scrubs the disk). A `MDFLY_CONFIG_DIR` env var (default `~/.mdfly/`) relocates the entire CLI state directory atomically — the recommended escape hatch for users whose home directory is synced to a third-party cloud (Dropbox / iCloud / OneDrive) and would otherwise leak credentials to that cloud. The compromised-credentials response path is: `mdfly logout --all` from a trusted machine revokes every server session; for anon Documents the user wants to durably protect, `mdfly claim <slug>` from a logged-in trusted machine transfers ownership to the session and NULLs the `edit_token_hash` (per [[Claim]] / ADR-0019), at which point session auth supersedes and the previously-leaked Edit Token is dead weight. Edit Token rotation without a Claim is **not** in v1; a `mdfly rotate-token` verb is deferred to v2 alongside the dashboard and is the natural future companion to the existing `mftk_` machinery.

We chose **mode-0600 plaintext** over **OS-keychain encryption** (macOS Keychain / Linux Secret Service / Windows DPAPI) because the upgrade in security floor is marginal — the realistic compromise paths for a target user are (a) malware running as you, against which keychain APIs offer essentially zero protection (the malware just asks the keychain too), (b) backup or cloud-sync exfiltration, against which keychain APIs offer real protection but `MDFLY_CONFIG_DIR` outside the synced root also offers real protection at zero engineering cost, and (c) cold disk forensics, against which keychain APIs offer real protection but the threat model for an indie markdown-sharing CLI does not include this attacker — while the cost of keychain integration is three platform code paths (CGO bindings or platform-shell-out for macOS, libsecret for Linux, DPAPI for Windows), a keychain-unlock prompt that breaks headless / SSH / `--device` flow (defeating the whole reason `--device` exists), and a forever-on engineering tax to keep three OS subsystems debugged. The industry baseline supports this choice: `gh`, `gcloud`, `claude`, `cargo`, `git`, `kubectl`, `aws` all ship mode-0600 plaintext credential files as their default, and have done so under significant security scrutiny for years. We chose **`--wipe-local` as a distinct flag** over **making it the default behavior of `logout`** because the L1-default (wipe session pointer only, keep Edit Tokens and Local State) preserves the legitimate non-shared-PC flow where a user logs out of their account but still wants to manage anon docs they published — destroying that map silently on every `logout` would be a footgun in the >95% case to defend the <5% case. We chose **`--wipe-local` over `--purge` or bare `--wipe`** because `--purge` is overloaded with package-manager semantics and bare `--wipe` is ambiguous between local-wipe and server-side-wipe-all; the verbose name is the unambiguous one. We chose to **preserve `config.toml` under `--wipe-local`** rather than scorch it, because the config file is opt-in (it never gets auto-written), contains no secrets, and represents a deliberate user choice the CLI shouldn't second-guess; a user who genuinely wants no-trace mode can `rm -rf ~/.mdfly/` themselves. We chose **`MDFLY_CONFIG_DIR` as an env var** rather than a `config.toml` setting because the entire problem is "where do we look for `config.toml` in the first place" — putting the config-dir location *inside* the config file is the obvious chicken-and-egg. The honest costs we accept: (a) backup snapshots and cloud-sync daemons running as the user will exfiltrate credentials by default, mitigated only by user-documented hygiene (do not sync `~/.mdfly/`, or relocate with `MDFLY_CONFIG_DIR`); (b) Edit Tokens cannot be rotated without Claim in v1 — a leaked `mftk_` for an anon Document the user does not wish to Claim is unrecoverable until that Document's 30-day expiry (per [[Anonymous Document]]); (c) the `--wipe-local` design preserves `config.toml`, so a paranoid "no trace" user must `rm -rf` themselves — accepted as the right default for the much more common case of "I want to log out of this shared PC" where the user's deliberate `config.toml` should survive the wipe. The trust-boundary stance is documented inline at every place a user would learn about it: the `CLI` term in CONTEXT.md, the dedicated [[Shared-PC Hygiene]] term, `mdfly login --help`, and the abuse / takedown page footer.
