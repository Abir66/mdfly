# View path: server-rendered Viewer chrome, `/llm/` raw-markdown twin, any file type may be Root

The human view path is **fully server-rendered Go HTML** — no SPA, no client router, no client-side manifest. On a hit to `mdfly.dev/<slug>[/<key>]` the backend reads the Bundle Manifest from Postgres, fetches the addressed blob from R2, resolves every logical reference (assets → absolute `storage.mdfly.dev/documents/<slug>/<hash>.<ext>`; cross-`.md` links → absolute `mdfly.dev/<slug>/<path>`), and renders through Goldmark (GFM + frontmatter + chroma highlighting + bluemonday sanitize, raw HTML stripped). Reference rewriting runs as a **Goldmark AST transformer** over `ast.Image` and `ast.Link` destinations before the HTML renderer, so one pass covers images and cross-document links, resolved against the page's own directory and the manifest's `project_root`. Preview Metadata (`<meta>` OpenGraph tags) is extracted from that **same render pass** — the body is being rendered anyway — rather than from cached columns, so per-page OG resolves for free. Every node is addressed by its **exact manifest key, extension included** (`docs/api/auth.md`, `assets/logo.png`); resolution is exact key → serve it, else a path that is a directory prefix of some key → a Directory Listing, else 404, with trailing slashes optional and 301-canonicalized. The page is a **Viewer chrome**: a collapsible left file-tree sidebar built **synthetically** from manifest keys (a directory exists iff a key shares its prefix — folders are never stored, so no schema or wire change), a breadcrumb, and a center column that **dispatches on node type** — markdown renders to HTML with a Raw toggle that lazy-fetches the byte-identical source blob from `storage.mdfly.dev` once and swaps it in via CSS; an image shows inline; a text or code file under `PreviewMaxBytes` (1 MB, decided from the manifest `size` with **no blob fetch** above the cap) and verified non-binary (valid UTF-8, no NUL bytes, sniffed *after* fetch to defend against a lying extension) renders as server-side chroma-highlighted source; anything oversize, binary, or unrecognized becomes a metadata card with a Download link to the CDN blob; a directory becomes a listing (folders first, then files with sizes) that auto-renders a `README.md`, else `index.md`, beneath it. **A Root may be any file type** — `mdfly publish report.pdf` and `mdfly publish main.go` are first-class, with no `root_kind` on the wire, because presentation is already resolved from the addressed key's extension plus the content sniff; the recursive-reference walk applies only to a markdown Root, since other types have no links to follow. `root_path` is **nullable** in the data model (an empty root serves a root Directory Listing) as forward-compat for a future folder publish; the v1 CLI never produces it, so it ships as server-side tolerance plus a fixture test. The sidebar uses native `<details>`/`<summary>` so folder collapse needs zero JS, with the server emitting `open` on the current file's ancestors and `aria-current` for highlight; the whole-sidebar rail collapse persists in `localStorage` applied by a tiny `<head>` snippet before paint (the one piece of state that must survive full-reload navigation), while per-folder state resets to the server default each load. Under 768 px the sidebar becomes a drawer behind a mobile top bar. Mermaid and KaTeX render client-side via lazy shims that boot only when the rendered HTML contains a diagram placeholder or math node; Viewer CSS and JS ship as **content-hashed external assets under `/_static/*`** with `Cache-Control: immutable`, fetched once and reused across navigations. A parallel **LLM twin** at `mdfly.dev/llm/<slug>[/<path>.md]` shares the exact same resolution pipeline but skips the HTML wrap and the sanitizer, returning resolved markdown as `text/plain; charset=utf-8` with cross-document links rewritten to sibling `/llm/` URLs, so an agent or `curl` can crawl a whole Document without a JavaScript runtime. Both families are pure functions of `(slug, key, manifest_hash)` and ship `Cache-Control: public, max-age=300, s-maxage=86400` so the edge absorbs the read fan-out; the backend renders once per Update for any popular Document, protected by single-flight per slug against cache stampede and by a render-time budget cap (over ~2s returns 500). Deleted and expired slugs return **410** on every route, never-existed return **404**.

We chose SSR over the original **inlined-manifest SPA** because AI agents are a first-class read consumer: agents and `curl` need self-contained markdown over HTTP without executing JavaScript, which the SPA's client-side link resolution made impossible without duplicating resolution on the server anyway — and once resolution moves server-side for agents, having the SPA also resolve client-side is duplicated work and the inlined JSON manifest is dead weight. We chose it over the half-step where the backend resolves and the SPA still renders, because that pays the JS-bundle and blank-flash cost without buying anything the backend cannot render itself, given the viewer has no interactive state beyond diagrams, math, and a copy button — all correct as progressive enhancements over static HTML. We **kept full-page-reload SSR even after the chrome became multi-page navigation**, because the chrome is a pure function of `(slug, key, manifest_hash)` and sits in the edge cache; a SPA would add a bundle, a flash, router-state bugs, and a duplicate resolution layer to buy soft-navigation that sub-100 ms cached reloads already deliver. We chose **not to render Mermaid or KaTeX server-side** because Mermaid in Go means a Node sidecar or WASM embedding and KaTeX ports add binary weight, while lazy JS keeps the no-JS floor for *content* and gates only *enrichment* — the correct progressive-enhancement boundary. We **inline the file tree into every page** rather than fetching it as JSON once, because inlining costs no extra request, no paint flash, and works with JS off, and every page is independently CDN-cached anyway; the repeated bytes are absorbed by gzip even for a 500-file Bundle. We chose **synthetic folders** over a stored directory structure because the CLI uploads no empty directories, so materializing folders would be untested schema weight; the accepted consequence is that a listing reflects manifest contents, not the publisher's on-disk tree. We **reversed an earlier strip-`.md` URL convention** in favor of exact keys because one uniform rule ("tree node → `/<slug>/<exact-key>`") with trivial file-versus-directory disambiguation beats a special case, and it matches the file browser the Viewer imitates; nothing had shipped publicly, so no links broke. We chose **external content-hashed static assets** over inlining CSS because the load shape inverted once navigation became multi-page: one inline block is cheap for a single document but re-downloads on every one of twenty page views, whereas an `immutable` external bundle is fetched once and served entirely by the CDN. We chose to **fetch the raw blob cross-origin from the CDN** over inlining both rendered and raw in the page (doubling every payload) or proxying a same-origin raw route (putting the server on that path); the cost is one R2 CORS rule allowing `https://mdfly.dev` (ADR-0011), and the exposed content hash leaks nothing that embedded assets do not already expose. We chose **server-side chroma over a client highlighter** because chroma is already in the stack and styled, so highlighting standalone code files adds zero client JS. We chose **any-type Root** over a markdown-only guard because the guard bought nothing — the center dispatch and render path already had to handle non-markdown nodes, since assets inside a bundle are viewed the same way — and it removed an arbitrary rejection users hit immediately ("why can't I just share this PDF?"). The costs we accept: math and diagrams paint one frame after the rest on first visit; the backend is on the hot path for cache misses, mitigated by edge caching and single-flight; navigation between documents is a full reload rather than client-routed; the resolution pipeline is wider than markdown-only, which is more surface to keep correct; `root_path` nullability ships dormant and only fixture-tested until folder publish exists; the Download affordance cannot force `Content-Disposition: attachment` cross-origin, so some types (PDF) open in-browser instead of saving; per-folder collapse state resets on navigation; the LLM twin **degenerates for non-text Roots** (an agent hitting `/llm/<slug>` for a binary gets a short "download at `<url>`" stub), diluting the "every Document has a clean agent-readable twin" story — judged acceptable because the twin stays fully meaningful for the markdown and text Roots that dominate real use, and a degenerate-but-honest stub beats refusing the publish; and the product-identity shift from "markdown sharing" toward "share any file, markdown gets special treatment" is real and worth recording.
