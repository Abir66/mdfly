# App-level identity-aware rate limiting on Redis

The backend adds a second rate-limiting layer (L2) in front of the write paths — `publish/init`, `update/init`, and `DELETE /documents/:slug` — beneath the Cloudflare edge rate-limit (L1, ADR-0021, 10 req/min per IP, IP-only). L2 is **identity-aware**: the key is the Edit Token on update/delete (the request already carries `Authorization: Bearer mftk_...`) and falls back to the caller's `CF-Connecting-IP` for anonymous publish (trusted only from Cloudflare's published IP ranges, since `RemoteAddr` behind the proxy is a Cloudflare edge IP, not the client). The store is **Redis, reached over a pooled RESP/TCP connection** configured by a single `REDIS_URL` — Upstash's TLS endpoint (`rediss://`) today, a local instance (`redis://`) if we ever self-host, which is a URL swap and no code change. Counting is fixed-window via one house method — `IncrementWithTTL(ops)` — that pipelines **all of a request's windows into a single round trip** (`INCR` + `EXPIRE` per window), where each key embeds a time-bucket step (`floor(now/window)`) so each window is a fresh key that self-resets. Two windows per subject: **10/min** and **30/hr**. On any Redis error the limiter **fails open** (allow the request). Read paths (SSR HTML, `/llm` twin, `cdn.mdfly.dev`) are never limited — they are served from edge cache and never touch the backend hot path.

We chose **Redis** over an in-process limiter because the limiter state must survive process restarts and be shared if the backend is ever scaled past one instance; it is free at our scale and adds no ops. This ADR originally specified Upstash's **HTTPS REST** transport, on the reasoning that it needs no persistent connection — which mattered under ADR-0007's DO App Platform. **ADR-0029 superseded that with an always-on Oracle VM**, where a long-lived pool is the natural fit and per-command HTTP framing is pure overhead, so the transport moved to RESP over a bounded TCP pool (10 connections, 2 kept warm, dial and command timeouts at 2s so a fail-open degradation stays bounded). The vendor is unchanged; the URL now selects the deployment, which is what makes the store swappable without touching the limiter. We chose **fixed-window with a time-bucketed key** over token-bucket or sliding-window because it collapses to `INCR`+`EXPIRE` with no read-modify-write and no Lua: the bucketed key makes the window self-resetting, so the `EXPIRE` exists only to garbage-collect dead keys — a missed `EXPIRE` leaks one stale key (memory), it can never permanently block a subject, because the next window is a different key. We chose to **batch every window into one round trip** rather than one call per window both to halve the store latency on the write path and because it is what makes "all windows are counted on every request" true: counting sequentially meant a failure on the per-minute window returned early and silently left the hourly allowance unspent, letting a caller hammer the minute window for free. We chose **fail-open** over fail-closed because rate limiting is abuse mitigation, not a correctness invariant; a Redis outage must degrade to "unthrottled" (L1 at the edge still stands), never to "all writes blocked" — a malformed `REDIS_URL`, by contrast, is a config error and does fail the boot. We chose an **identity key with IP fallback** because an Edit Token identifies the actual editor across IPs, while anonymous publish has no identity to key on and IP is the only signal available — with the `CF-Connecting-IP` caveat that the real client IP must be read from the Cloudflare header, not the TCP peer.
